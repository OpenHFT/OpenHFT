== Recorded Decisions

=== SMOKE-DEC-001 Dedicated smoke test module

Date:: 2025-11-29
Context:: The third-party BOM must stay usable on Java 8, but the set of dependencies evolves and can drift in bytecode level or transitive requirements.
Without continuous validation, regressions would only be detected when downstream consumers attempt to use the BOM.
Decision Statement:: Create dedicated `third-party-smoke` module with class loading and minimal usage tests to validate Java 8 compatibility continuously.
Alternatives Considered::
* Manual spot checks:
** *Pros:* No automated test maintenance.
** *Cons:* Error-prone, inconsistent, no CI gate.
* Rely on downstream consumers:
** *Pros:* No extra module to maintain.
** *Cons:* Late detection of breakage, poor developer experience.
* CI-only validation without committed tests:
** *Pros:* Keeps repository lightweight.
** *Cons:* No local reproducibility, unclear coverage.
Rationale for Decision:: Fast feedback loop prevents regressions.
Validates transitive dependencies.
No external service dependencies.
Developers can run locally before pushing.
Impact & Consequences:: Contributors must keep tests green.
Build time increases ~15-30 seconds.
Version bumps that break Java 8 fail fast with clear error messages.
Notes/Links:: Module path `third-party-smoke`.
See requirement `SMOKE-TEST-001` in project-requirements.adoc.

=== SMOKE-DEC-002 Separate class loading and usage tests

Date:: 2025-11-29
Context:: Class loading proves artifact resolution and bytecode compatibility but not runtime behaviour.
Some libraries may load successfully but fail when actually used due to API changes, missing resources, or runtime assumptions.
Decision Statement:: Maintain `ClassLoadingSmokeTest` (85+ tests) for comprehensive coverage and `MinimalUsageSmokeTest` suite for behavioural validation of critical dependencies.
Alternatives Considered::
* Class loading only:
** *Pros:* Faster, simpler test suite.
** *Cons:* Misses runtime issues, API breakage, resource loading problems.
* Full integration tests:
** *Pros:* Complete behavioural coverage.
** *Cons:* Slow, requires external services, brittle, expensive to maintain.
* Combined approach (current):
** *Pros:* Fast comprehensive class loading + targeted behavioural validation.
** *Cons:* Two test layers to maintain.
Rationale for Decision:: Class loading is fast (85+ tests in ~1.3s) and proves basic compatibility.
Minimal usage tests catch runtime issues without external dependencies.
Balance between speed and confidence.
Impact & Consequences:: Two test layers require maintenance.
Minimal usage tests focus on frequently-used artifacts.
Less-common artifacts rely on class loading only.
Notes/Links:: `ClassLoadingSmokeTest.java` (85+ dynamic tests), `Minimal*SmokeTest.java` (25+ tests across 6 categories).

=== SMOKE-DEC-003 Categorised minimal usage tests

Date:: 2025-11-29
Context:: `MinimalUsageSmokeTest` grew to 25+ tests covering disparate technologies (observability, serialisation, networking, logging, utilities, database).
Single file became difficult to navigate and didn't align with dependency groupings.
Decision Statement:: Split minimal usage tests into category-based test classes: `MinimalObservabilitySmokeTest`, `MinimalSerializationSmokeTest`, `MinimalNetworkingSmokeTest`, `MinimalLoggingSmokeTest`, `MinimalUtilitiesSmokeTest`, `MinimalDatabaseSmokeTest`.
Alternatives Considered::
* Single monolithic test class:
** *Pros:* One file, simpler structure.
** *Cons:* Poor navigation, unclear grouping, difficult to execute categories independently.
* Package-based organisation (separate packages):
** *Pros:* Strong separation.
** *Cons:* Over-engineered for 6 test classes, unnecessary complexity.
* Artifact-based organisation (one class per dependency):
** *Pros:* Maximum granularity.
** *Cons:* Too many files (80+ test classes), maintenance burden.
Rationale for Decision:: Category-based organisation aligns with dependency groupings in pom.xml and `ClassLoadingSmokeTest` helper methods.
IDE navigation and test execution become clearer.
Parallel execution can target specific categories.
Impact & Consequences:: More test files (6 classes instead of 1).
Clearer test organisation and reporting.
Easier to add new tests to appropriate category.
Notes/Links:: Test classes in `src/test/java/net/openhft/thirdparty/smoke/`.
See requirement `SMOKE-TEST-002` in project-requirements.adoc.

=== SMOKE-DEC-004 Hardcoded dependency versions

Date:: 2025-11-29
Context:: Several dependencies (JCommander 1.48, Gson 2.8.2, Unirest 1.4.9, Joda-Time 2.14.0, Commons Email 1.5, JGit 5.13.0.202109080827-r, Maven Model 3.6.3) were found in peer modules but not managed in `third-party-bom`.
These represent actual usage patterns in the Chronicle ecosystem.
Decision Statement:: Keep hardcoded versions in `pom.xml` as "additional peer tests" until `third-party-bom` is updated to manage these dependencies.
Alternatives Considered::
* Remove from smoke tests:
** *Pros:* Cleaner pom.xml, no version maintenance.
** *Cons:* Loses validation of real peer module dependencies.
* Add to third-party-bom immediately:
** *Pros:* Centralized version management.
** *Cons:* Requires BOM update decision, may include unwanted dependencies.
* Create separate smoke module for peer dependencies:
** *Pros:* Clear separation of concerns.
** *Cons:* Over-engineered, unnecessary complexity for 7 dependencies.
Rationale for Decision:: Validates real usage patterns.
Documents version drift between peer modules and BOM.
Provides evidence for future BOM migration.
Tests remain green with known versions.
Impact & Consequences:: Version maintenance burden in smoke module pom.xml.
Documented in version-issues.adoc with migration path.
Requires manual version updates when peer modules change.
Status:: Resolved by moving peer dependency versions into `third-party-bom` and relying on BOM-managed versions in the smoke tests.
Notes/Links:: See the `pom.xml` section "Additional third-party jars observed in peer modules".
Documented in version-issues.adoc.
See requirement `SMOKE-NF-O-003` for documentation currency.

=== SMOKE-DEC-005 Bytecode enforcement with exclusions

Date:: 2025-11-29
Context:: HSQLDB and MongoDB bson-record-codec ship with Java 11+/17 bytecode, exceeding Java 8 baseline.
Complete rejection would break legitimate use cases (HSQLDB has jdk8 classifier; bson-record-codec may be transitive-only).
Decision Statement:: Use `enforceBytecodeVersion` with explicit exclusions for HSQLDB and bson-record-codec, documented in version-issues.adoc with action items to investigate alternatives.
Alternatives Considered::
* Remove dependencies entirely:
** *Pros:* Pure Java 8 bytecode compliance.
** *Cons:* Breaks HSQLDB validation, may exclude legitimate use cases.
* Require Java 8 variants for all dependencies:
** *Pros:* Strict enforcement.
** *Cons:* Not all libraries provide Java 8 variants; blocks upgrades.
* Skip bytecode enforcement:
** *Pros:* No exclusion management.
** *Cons:* Silent Java 8 breakage, defeats purpose of smoke tests.
Rationale for Decision:: Balanced approach - enforce for most artifacts, document exceptions, alert on new violations.
Exceptions require justification and follow-up.
HSQLDB provides jdk8 classifier. bson-record-codec may be transitive and unused.
Impact & Consequences:: Explicit exclusion list in `pom.xml`. Requires documentation updates when adding exclusions.
Notes/Links:: See `maven-enforcer-plugin` configuration in pom.xml.
Documented in version-issues.adoc.
See requirement `SMOKE-NF-O-001` in project-requirements.adoc.

=== SMOKE-DEC-006 Focused smoke tests for specific technologies

Date:: 2025-12-24
Context:: Beyond the `Minimal*SmokeTest` category-based tests, some dependencies require more detailed validation or have complex integration scenarios that don't fit cleanly into a category.
A single test method per file allows targeted execution and clearer failure diagnostics.
Decision Statement:: Create focused smoke test classes for specific technologies: testing frameworks (JUnit variants, Mockito, EasyMock, PowerMock), serialisation libraries (Jettison), networking stacks (OkHttp, Jetty WebSocket, NIO stacks), build tools (JMH, ProGuard), and specialized utilities (ClassGraph, JavaPoet, JavaxInject, OSGi/Pax).
Alternatives Considered::
* Add to Minimal* category tests:
** *Pros:* Fewer files, simpler structure.
** *Cons:* Categories become bloated; failure messages less specific; harder to run individual library tests.
* One test class per dependency (artifact-level granularity):
** *Pros:* Maximum clarity and isolation.
** *Cons:* Too many files (80+); many would have only 1-2 tests.
* Keep only ClassLoadingSmokeTest:
** *Pros:* Minimal test maintenance.
** *Cons:* Misses runtime behaviour issues; insufficient for complex integrations.
Rationale for Decision:: Focused tests complement category tests by providing deeper validation for:
* Libraries with complex setup/teardown (Jetty, Grizzly, Netty)
* Testing frameworks that themselves test (JUnit launcher, Mockito mocks)
* Libraries requiring specific usage patterns (JMH options, ProGuard configuration)
* Dependencies with known integration complexity (OSGi, PowerMock)
Each focused test remains small (typically 20-90 lines) but provides clear, isolated validation.
Impact & Consequences:: 27 focused test files in addition to 6 Minimal* tests.
IDE navigation by class name maps directly to library under test.
Parallel test execution can target specific technologies.
New contributors should add focused tests for complex libraries, category tests for simple ones.
Notes/Links:: Focused tests in `src/test/java/net/openhft/thirdparty/smoke/`.
See requirement `SMOKE-TEST-002` in project-requirements.adoc.

=== SMOKE-DEC-007 Shared test fixtures and constants

Date:: 2025-12-24
Context:: Multiple test files defined similar POJO classes (`SimplePojo`, `Person`, `CliArgs`) and constants (`DELTA`, test values) independently, leading to duplication and inconsistent implementations.
Decision Statement:: Extract shared test fixtures to `SmokeTestFixtures.java` and shared constants to `SmokeTestConstants.java` for reuse across the test suite.
Alternatives Considered::
* Keep inline definitions:
** *Pros:* Each test is self-contained.
** *Cons:* Duplication; inconsistent implementations; harder to maintain.
* Abstract base test class:
** *Pros:* Inheritance provides shared behaviour.
** *Cons:* Over-engineered for simple fixtures; limits test class design.
* Per-category fixture classes:
** *Pros:* Fixtures aligned with test categories.
** *Cons:* Creates 6+ fixture classes for ~5 shared types; artificial boundaries.
Rationale for Decision:: Single shared fixtures file is sufficient for the small number of shared types.
Constants interface centralises magic numbers.
Tests remain easy to read by importing specific fixtures.
Future shared types have a clear home.
Impact & Consequences:: Tests should import from `SmokeTestFixtures` and `SmokeTestConstants` rather than defining local copies.
Existing inline definitions can be migrated incrementally.
Notes/Links:: `SmokeTestFixtures.java` and `SmokeTestConstants.java` in test sources.

=== SMOKE-DEC-008 SLF4J bindings isolated via profiles

Date:: 2025-12-13
Context:: The smoke tests must keep build output clean (no warnings) while still validating multiple SLF4J bindings used across the ecosystem.
Keeping multiple SLF4J providers on the same test classpath triggers "multiple bindings" warnings, which makes log review harder and can hide real issues.
Decision Statement:: Validate SLF4J bindings one at a time via Maven profiles (`slf4j-simple` by default, `slf4j-nop` on demand) and assert that exactly one provider is present.
Alternatives Considered::
* Keep multiple bindings together:
** *Pros:* Matches a "worst-case" classpath.
** *Cons:* Produces warnings and makes clean builds impossible.
* Pick a single binding and drop the rest:
** *Pros:* Clean output.
** *Cons:* Loses validation of the other binding(s) used by downstream consumers.
* Attempt to suppress SLF4J warnings:
** *Pros:* Noisy output reduced.
** *Cons:* Fragile and may vary across SLF4J versions.
Rationale for Decision:: Keeps logs clean while still validating both bindings.
Avoids hiding genuine warnings in CI output.
Impact & Consequences:: CI should run at least the default binding and the alternative binding profile.
Developers can reproduce issues by selecting the relevant profile.
Notes/Links:: See `pom.xml` profiles `slf4j-simple` and `slf4j-nop`.
Documented in version-issues.adoc and enforced by requirement `SMOKE-NF-O-004`.
