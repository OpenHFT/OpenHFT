= Meaningful Message Check Requirements
:toc:
:toclevels: 3
:sectnums:

== Overview

This document specifies requirements for the Meaningful Message Check, a Checkstyle-based assertion message quality checker.
The goal is to detect low-signal assertion messages that provide little diagnostic value when tests fail,
and encourage developers to write meaningful messages that explain the invariant being tested.

=== Scope

The check analyses messages in:

* Assertion methods (JUnit, AssertJ, etc.)
* Java `assert` statements (`assert condition : "message";`)
* Preconditions such as `Objects.requireNonNull` and `requireNotNull`
* `throw new <Exception/Error>(message)` constructor calls
* JUnit annotation descriptions (e.g., `@DisplayName`, `@ParameterizedTest(name=...)`,
  `@RepeatedTest(name=...)`, `@Disabled`, `@Ignore`, and `disabledReason` attributes)
* Javadoc first paragraphs (top-level classes and members)
* Log sites (SLF4J `Logger.trace/debug/info/warn/error`, Log4j2 `Logger.trace/debug/info/warn/error/fatal`,
  JUL `java.util.logging.Logger` levels, `System.Logger.log(Level, ...)`, and Chronicle
  `Jvm.debug/warn/error/startup/perf().on(...)` callsites)

Precondition messages for `requireNonNull`/`requireNotNull` are exempt from message-quality rules
when the message exactly matches the checked parameter name.

Duplicate detection is scoped per message source so display names do not collide with assertion or throw messages.

Javadoc first paragraphs are evaluated by redundancy (class/member), duplicate, long-word, and word-count rules only.

=== Log Site Behaviour

Log site checks apply to:

* SLF4J `Logger.trace`, `Logger.debug`, `Logger.info`, `Logger.warn`, `Logger.error`
* Log4j2 `Logger.trace`, `Logger.debug`, `Logger.info`, `Logger.warn`, `Logger.error`, `Logger.fatal`
* JUL `java.util.logging.Logger.log(Level, ...)` plus convenience methods (`severe`, `warning`, `info`,
  `fine`, `finer`, `finest`)
* `System.Logger.log(Level, ...)` including supplier variants
* Chronicle `Jvm.debug/warn/error/startup/perf().on(...)` callsites

`trace` and `info` are in scope by default (same standard as `debug`);
`Jvm.startup()` and `Jvm.perf()` are included as dedicated channels.

Message requirement rules:

* For `Jvm.*.on(...)` callsites (class or logger overloads), require a non-null message or a
  throwable. Empty templates are treated as messages and evaluated by the MM rules.
* For SLF4J, Log4j2, JUL, and System.Logger:
** A null template is a missing message (MMMissingMessage) unless a known throwable is present.
   Additional arguments do not satisfy the missing-message rule.
** An empty template (`""`) is still a message and is evaluated by MMTooShort or
   MMTooFewMeaningfulWords.
* If a throwable is present, the message is optional; when present, it must meet the log-site MM subset.
* For these loggers, apply the log-site MM subset to non-null templates with no varargs, even for
  constant strings.

Throwable handling rules:

* For SLF4J, Log4j2, JUL `log(Level, String, Object...)`, and `System.Logger.log(Level, String, Object...)`
  varargs, treat each argument as a placeholder; do not infer a throwable by position.
  Missing-message checks apply whenever the template is null and no known throwable is present.
* `Jvm.*.on(...)` overloads define throwable presence by signature.

Hot-path code may suppress the message-required rule at class or method level to avoid forced message
construction; if a message is provided, quality checks still apply.

Placeholder handling for logs:

* Treat `{}` as meaningful placeholders (SLF4J/Log4j2).
* Allow numeric placeholders like `{0}` when present.
* Treat printf-style `%s` as meaningful placeholders.

Message handling for logs:

* `Jvm.*.on(clazz, null, throwable)` treats the message as absent (allowed).
* `Jvm.*.on(clazz, "", throwable)` is a present message and fails via MMTooShort/MMTooFewMeaningfulWords.
* `Jvm.*.on(clazz, "")` or `Jvm.*.on(clazz, "", null)` is a present but empty message and is evaluated by
  MMTooShort/MMTooFewMeaningfulWords.
* `Jvm.*.on(clazz, null)` or `Jvm.*.on(clazz, null, null)` is missing a message (fail missing-message rule).
* `Jvm.*.on(clazz, throwable)` is allowed; the throwable is assumed to carry a meaningful message.
* The same rules apply to `Jvm.*.on(logger, ...)` overloads.
* For SLF4J, Log4j2, JUL, and System.Logger, a null template is missing a message unless a known
  throwable is supplied (all levels).
* For these loggers, a null template with any known throwable argument is allowed; the throwable is
  assumed to carry a meaningful message.
* For these loggers, a null template with arguments but no known throwable is a missing message
  (MMMissingMessage). "Known throwable" means any subtype of `Throwable` (including custom types like
  `StackTrace`), determined by type only (no name-based guessing).
* Empty templates (`""`) are treated as messages and fail via MMTooShort or MMTooFewMeaningfulWords.
* For `System.Logger` supplier variants, treat the supplier as message presence. Only evaluate the
  message when the supplier returns a compile-time constant string; otherwise treat it as a dynamic
  placeholder.
* Initial checks should focus on string literals and compile-time constants. For simple concatenations,
  treat dynamic elements as placeholders that count as meaningful tokens.

Missing message rule (MMMissingMessage):

* Add a dedicated rule to flag missing messages: `MMMissingMessage`.
* Apply this rule to JUnit `fail()` and `assertXxx(...)` callsites when no message argument
  is supplied or the message is explicitly `null` (JUnit 4 and JUnit 5).
* Apply this rule to `throw new` statements when no non-Throwable message argument is supplied
  (message-less or cause-only constructors).
* Apply this rule to all `Jvm.*.on(...)` callsites (class and logger overloads) when the message
  is null and no throwable is provided; placeholders do not satisfy it.
* Apply this rule to SLF4J, Log4j2, JUL, and System.Logger callsites when the template is null and
  no known throwable is supplied (additional arguments do not satisfy the rule).
* For `System.Logger` supplier overloads, a null supplier with no throwable is a missing message;
  non-null suppliers are treated as message presence.
* Apply this rule to annotation descriptions when a reason is omitted (for example, `@Disabled` without
  a value). Empty strings are treated as present and fail via MMTooShort/MMTooFewMeaningfulWords.
* SLF4J, Log4j2, JUL, and System.Logger empty templates are handled by
  MMTooShort/MMTooFewMeaningfulWords instead.
* An inline block comment with a real reason word inside the argument list (for example,
  `throw new IllegalArgumentException(/* condition not met */);`) suppresses MMMissingMessage.
  Empty comments and line comments do not suppress. Use this sparingly for low-level or
  performance-sensitive call sites.
* Priority: MMMissingMessage is highest priority and suppresses other MM warnings for that site.

Message extraction output:

* When `messageExtractionFile` is set or the `mm.extract.file` system property is provided, the
  checker writes TSV records for each message it evaluates.
* Columns: `file`, `line`, `source`, `chars`, `words`, `meaningful`, `placeholders`,
  `keyValueLabels`, `totalWords`, `effectiveMeaningful`, `message`.
* Unset or unresolved values disable output so normal builds are unaffected.

Scope restrictions:

* Direct `Jvm.*().on(...)` callsites only; `ExceptionHandler.on(...)` callsites are out of scope.

=== Test Metadata Placeholders

For `@DisplayName`, `@Disabled`, and parameterised/repeated names, placeholder tokens count as meaningful
words. Allow the JUnit standard set: `{index}`, `{arguments}`, `{argumentsWithNames}`, `{displayName}`,
and numeric placeholders like `{0}` and `{1}`.

Enable Surefire phrased-name reporting via the `quality` profile so XML outputs use phrased
method names while keeping class names stable for TeamCity grouping.

Missing metadata rules:

* `@Disabled` or `@Ignore` with no reason triggers MMMissingMessage.
* Empty reasons are treated as present and fail via MMTooShort/MMTooFewMeaningfulWords.

=== Rollout Defaults (release/2026.XYZ)

* Apply checks to existing code to address tech debt (no "new code only" gating).
* Include `info` and `trace` at the same standard as `debug`.
* Do not infer throwable position for SLF4J, Log4j2, JUL, or System.Logger; treat varargs as
  placeholders and apply missing-message checks when the template is null and no known throwable is present.
* Keep `ExceptionHandler.on(...)` callsites out of scope; only direct `Jvm.*.on(...)` callsites.
* All MeaningfulMessage findings are reported at warning severity and fail the build only when
  `quality.enforced=true` (consistent with the Maven Checkstyle configuration).

=== Rationale

When a test fails, the assertion message is often the first (and sometimes only) information a developer sees.
Low-quality messages like `"value"`, `"should be true"`, or `"L42"` force developers to:

* Open the source file and find the failing line
* Understand the test context from surrounding code
* Mentally reconstruct what the assertion was checking

Good messages eliminate this friction by explaining:

* What invariant is being tested
* What the expected state should be
* Why this matters (business context)

== Detection Rules

=== Rule 1: Duplicate Messages

Identical assertion messages within the same file indicate copy-paste without thought.

[source,java]
----
// BAD - duplicate message
assertEquals(expected1, actual1, "check value");  // line 10
assertEquals(expected2, actual2, "check value");  // line 20 - duplicate!
----

*Detection:* Track all assertion message strings; flag second and subsequent occurrences.

*Message:* `Duplicate assert message "{0}" (first used at line {1}). Each assert should have a unique message.`

=== Rule 2: Redundant Class/Method Name (Substance Analysis)

Messages that rely heavily on the class or method name provide little value because this information
is already in the stack trace. The checker uses *substance analysis* to determine if the message
has enough meaningful content without the name.

[source,java]
----
class BytesStoreTest {
    void testWriteBuffer() {
        // BAD - no substance without class name
        assertTrue(result, "BytesStore should be valid");
        // → only 1 meaningful word: "valid" (filler: should, be)

        // BAD - no substance without method name
        assertTrue(result, "testWriteBuffer");
        // → nothing remains after removing the name

        // GOOD - substance remains without the names
        assertTrue(result, "buffer should preserve byte order after write");
    }
}
----

==== Name Variant Detection

The checker detects multiple variants of the class/method name:

|===
|Original |Variants Checked

|`BytesStore` (class)
|`BytesStore`, `bytesStore` (field), `bytesstore` (lowercase), `BYTESSTORE` (uppercase)

|`getValue` (method)
|`getValue`, `GetValue` (class-style), `getvalue` (lowercase), `GETVALUE` (uppercase)
|===

==== Filler Word Filtering

Words that add no diagnostic value are filtered out when analyzing substance:

[cols="1,3"]
|===
|Category |Words

|Articles & Prepositions
|a, an, the, is, are, was, were, be, been, to, of, in, for, on, at, by, with, from, as, if, or, and, not, no, when, after, before

|Test-Related Generic
|should, must, expected, actual, value, result, test, check, assert, equals, return, returns, error, fail, failed, failure, exception, null, true, false, non, empty

|Structural Words
|have, has, does, contain, contains, exist, exists, present, set, get, first, second, one, two, more, only, all, without, within

|Low-Value Context
|line, method, class, assertion, occurred, here, call, new, instance, created, successfully
|===

Filler words are not a violation on their own; they are ignored when counting meaningful words.
They still count toward total word count checks. The requirement is 2+ non-filler words remaining
after removing the class or method name.

==== Diagnosis Types

The checker provides context-aware diagnosis messages:

|===
|Situation |Diagnosis

|Nothing left after removing name
|`nothing remains after removing the name`

|Only filler words remain
|`only filler words remain: should, be`

|No filler words, just too short
|`too short - only 1 word(s): valid`

|Filler words present but still too short
|`only 1 meaningful word(s): valid (filler: should, be)`
|===

*Requirement:* At least 2 meaningful (non-filler) words must remain after removing the class/method name.
Filler words do not count toward this minimum.

=== Rule 3: Redundant Line Number

Line numbers are redundant because the stack trace already shows them.

[source,java]
----
// BAD - line number in message
assertEquals(5, count, "L42");
assertEquals(5, count, "line 42");
assertEquals(5, count, "MyTest.java:42");
----

*Detection Pattern:*
----
(?i)(?:
    \bline\s+#?\d+|           # "line 42", "line #42"
    \bL\d+\b|                 # "L42" shorthand
    \.java:\d+|               # "File.java:42"
    \.kt:\d+|                 # "File.kt:42"
    \.scala:\d+               # "File.scala:42"
)
----

NOTE: Patterns like `Line1`, `Level2`, `Kernel32` are NOT flagged (no word boundary after number, or part of identifier).

=== Rule 4: Trivial Supplier

JUnit 5 supports `Supplier<String>` for lazy message evaluation. A trivial supplier that just returns
a constant string, a simple concatenation with a string literal, or a cheap expression with no
literals defeats this purpose.

[source,java]
----
// BAD - trivial supplier (constant string)
assertEquals(1, 1, () -> "constant message");
assertEquals(1, 1, () -> "prefix " + "suffix");  // still constant
assertEquals(1, 1, () -> "value: " + value);
assertEquals(1, 1, () -> name);
assertEquals(1, 1, () -> left + right);

// GOOD - dynamic message (lazy evaluation justified)
assertEquals(expected, actual,
    () -> "mismatch at index " + index + ": expected " + formatValue(expected));
----

*Detection:* No-arg lambda where the body is a string literal, literal-only concatenation,
literal + placeholder concatenation, or a simple identifier/concatenation with no literals.
The report summarises the constant parts.

=== Rule 5: Generic Single-Word Messages

Single-word messages that are just variable names or generic terms provide no context.

[source,java]
----
// BAD - too generic
assertEquals(expected, actual, "actual");
assertEquals(expected, actual, "value");
assertTrue(condition, "test");
----

*Detection Pattern:*
----
(?i)^(actual|expected|value|result|data|object|condition|
      test|check|message|msg|err|error|fail|ok|true|false)$
----

=== Rule 6: Assertion Type Repetition

Messages that just restate what the assertion method does.

[source,java]
----
// BAD - restates assertion type
assertEquals(5, count, "assertEquals");
assertTrue(flag, "should be true");
assertFalse(flag, "is false");
assertNotNull(obj, "not null");
----

*Detection Pattern:*
----
(?i)(
    ^assert(equals|true|false|null|notnull|same|notequals?|that)?$|
    ^should (be )?(equal|true|false|null|not null|same|the same)$|
    ^should not be null$|
    ^must (be )?(equal|true|false|null|not null|same|the same)$|
    ^must not be null$|
    ^(should|must|expected to) match$|
    ^values? (should|must) match$|
    ^equals?$|
    ^not null$|
    ^is null$|
    ^is true$|
    ^is false$
)
----

=== Rule 7: Index-Only Messages

Messages that are just array/list indices without context.

[source,java]
----
// BAD - just an index
assertEquals(expected, actual, "0");
assertEquals(expected, actual, "[0]");
assertEquals(expected, actual, "index 5");
----

*Detection Pattern:*
----
^(\d+|\[\d+\]|index\s*\d+|element\s*\d+|item\s*\d+|#\d+|i=\d+)$
----

NOTE: Messages with context like `"first entry should be header"` or array values like `"[a, b, c]"` are NOT flagged.

=== Rule 8: Contextless Comparison Messages

Messages that describe the action but not the meaning.

[source,java]
----
// BAD - doesn't explain what's being compared
assertEquals(expected, actual, "comparison");
assertEquals(x, y, "values should match");
assertEquals(a, b, "validation");
----

*Detection Pattern:*
----
(?i)^(
    comparison|check|validation|equality|verify|test|
    values? (should |must )?(match|equal|be equal)|
    (should|must) (be )?equal|
    not equal|
    mismatch|
    failed|failure|error
)$
----

=== Rule 9: Word Count Limits

Messages should be neither too terse nor too verbose, and should contain enough meaningful words.

|===
|Source |Minimum total |Minimum meaningful |Rationale

|Assertions/Preconditions
|4 words/placeholders
|2 meaningful words/placeholders
|Assertions should state subject + behaviour

|Throw
|2 words/placeholders
|1 meaningful word/placeholder
|Throws can be terse but must name the issue

|Annotations
|6 words/placeholders
|4 meaningful words/placeholders
|Display names and disable reasons should be descriptive

|Top-level class Javadoc first paragraph
|10 words/placeholders
|8 meaningful words/placeholders
|Class overviews should be descriptive

|Member Javadoc first paragraph
|6 words/placeholders
|4 meaningful words/placeholders
|Member summaries should be descriptive

|Logs
|4 words/placeholders
|2 meaningful words/placeholders
|Log templates need enough context for triage
|===

Maximum: 42 words/placeholders for all sources. Filler words do not count toward the meaningful minimums.
Only the first top-level type Javadoc in a file uses the class minimum; subsequent type and member Javadocs
use the member minimum.

[source,java]
----
// BAD - too short (2 words)
assertEquals(5, count, "count ok");

// BAD - too few meaningful words (only 1 meaningful word)
assertTrue(valid, "should be ok");

// BAD - too long (>42 words)
assertEquals(5, count, "the count value returned from the method should match the expected result we calculated earlier after applying filters, rounding rules, and post processing checks for the active user list in the final report including any adjustments for missing entries and archived records from last week");

// GOOD
assertEquals(5, count, "active user count after filtering inactive users");
----

NOTE: Word count checks are skipped if a more specific semantic warning (e.g., generic, restates assertion) already fired for the same message.

=== Rule 10: Long Word Detection

Words exceeding 42 characters are likely class or method names that should not appear in messages.

[source,java]
----
// BAD - contains long word (likely class name)
assertEquals(expected, actual, "ConfigurationManagerService failed");

// GOOD - descriptive text instead
assertEquals(expected, actual, "config service should return cached value");
----

*Threshold:* 42 characters

NOTE: Words matching the current class or method name are already flagged by Rule 2 and are not double-flagged.

=== Rule 11: Duplicates Assertion Input

Messages that just echo an expected value or variable name add no diagnostic value because assertion output already shows the inputs.

[source,java]
----
// BAD - duplicates input
assertEquals("admin", role, "admin");
assertEquals(expected, actual, "expected");
----

*Detection:* Message matches a single input literal or variable name without added context.

=== Rule 12: assertAll Heading Quality

JUnit 5 `assertAll` headings should describe the scenario being validated.

[source,java]
----
// BAD - low-signal heading
assertAll("checks",
        () -> assertEquals(1, one),
        () -> assertEquals(2, two));

// GOOD
assertAll("round-trip serialisation",
        () -> assertEquals(expected, actual));
----

*Detection:* Heading is generic (e.g., "check", "validation", "assertions").

=== Rule 13: Restates Derived Assertion

Derived assertions already encode the condition; repeating it adds no value.

[source,java]
----
// BAD - restates derived assertion
assertThat(list).as("empty").isEmpty();
----

*Detection:* Message restates derived assertion keywords like empty/present/contains.

=== Rule 14: AssertJ Generic Override

AssertJ override messages (`withFailMessage`, `overridingErrorMessage`) replace rich diff output.

[source,java]
----
// BAD - generic override
assertThat(actual).withFailMessage("failure").isEqualTo(expected);
----

*Detection:* Override message is generic or low-signal.

=== Rule 15: Missing Comparison Values

Comparison assertions should include operand values when the message is constant.

[source,java]
----
// BAD - missing operand values
assertTrue(a > b, "should be greater");
----

*Detection:* Comparison expression with constant message lacking operands.

=== Rule 16: Missing String Search Value

String search assertions should include the actual string in the message.

[source,java]
----
// BAD - missing string value
assertTrue(text.contains("@"), "should contain @");
----

*Detection:* contains/startsWith/endsWith with constant message and no string value.

=== Rule 17: Missing Loop Index

Assertions inside indexed loops should include the index in the message.

[source,java]
----
for (int i = 0; i < items.length; i++) {
    assertNotNull(items[i], "item should be present");
}
----

*Detection:* Indexed loop assertion with constant message missing index.

=== Rule 18: Missing Subject

Messages starting with "should" or "must" need a subject.

[source,java]
----
// BAD - missing subject
assertTrue(ok, "should be true");
----

*Detection:* Message starts with modal verb without subject.

=== Rule 19: Whitespace Run

Messages should avoid repeated whitespace runs.

[source,java]
----
// BAD - repeated whitespace
assertEquals(expected, actual, "order  should persist");

// GOOD
assertEquals(expected, actual, "order should persist");
----

*Detection:* Message contains two or more whitespace characters in a row.

===== MMDuplicatesInput: Message Duplicates Assertion Input

Message duplicates a literal expected value, variable name, or exception class.

.Examples
[source,java]
----

// BAD - duplicates variable name

// BAD - duplicates exception class

.Detection approach
* For common signatures, check if message literal equals:
** A literal expected value
** The simple identifier name of expected/actual
** The simple exception class name in assertThrows

===== MMLowSignalAssertAllHeading: assertAll Heading Quality

JUnit `assertAll(String heading, ...)` includes the heading in failure reports.

.Examples
[source,java]
----

    () -> assertEquals(a, b),
    () -> assertEquals(c, d));

// GOOD - describes scenario
assertAll("round-trip serialisation: header + trailer",
    () -> assertEquals(a, b),
    () -> assertEquals(c, d));
----

.Detection approach
* Run headings through existing semantic rules (generic/restates/contextless/too-short)
* If assertAll has N>=3 executables and heading is absent, emit suggestion (not error)

===== MMRestatesDerivedAssertion: Restates Derived Assertion

Expand "restates assertion" to common derived patterns that frameworks already show.

.Patterns to detect
----

^not empty$
^(is )?blank$
^not blank$
^(is )?present$
^contains$
^matches$
----

.Examples
[source,java]
----

===== MMAssertJGenericOverride: AssertJ Generic Override

AssertJ docs note that `as(...)` descriptions preserve rich diff output, while `withFailMessage()`/`overridingErrorMessage()` can hide context.

.Detection approach
* If `.withFailMessage(...)` or `.overridingErrorMessage(...)` message is generic/too-short/restates, suggest `.as(...)` instead

.Reference
* https://assertj.github.io/doc/[AssertJ documentation]

===== MMMissingComparisonValues: Missing Comparison Values

Constant messages for comparison assertions should include operand values.

.Examples
[source,java]
----

----

.Detection approach
* If `assertTrue/assertFalse` uses a comparison expression and the message is constant, require operand values in the message.

===== MMMissingStringSearchValue: Missing String Search Value

String search assertions should include the searched string or the actual value.

.Examples
[source,java]
----
// BAD - missing string value

----

.Detection approach
* For contains/startsWith/endsWith with constant messages, require the searched string or target value to appear in the message.

===== MMMissingLoopIndex: Missing Loop Index

Assertions inside indexed loops should include the loop index in the message.

.Examples
[source,java]
----
for (int i = 0; i < items.length; i++) {

----

.Detection approach
* If an assertion is inside an indexed loop and the message is constant, require the index variable in the message.

===== MMMissingSubject: Missing Subject

Messages starting with "should" or "must" need a subject.

.Examples
[source,java]
----
// BAD - missing subject

=== Suppression

Suppressions can be configured via:

1. Checkstyle suppression filters (file-level)
2. `@SuppressWarnings("checkstyle:MeaningfulMessage")` to suppress the check entirely (method/class-level, legacy)
3. `@SuppressWarnings("MM-all")` or `@SuppressWarnings("checkstyle:MM-all")` to suppress MeaningfulMessage rules only
4. `@SuppressWarnings("MMTooShort")`, `@SuppressWarnings("MMGenericMessage")`, etc. for per-rule suppression
5. Inline `// CHECKSTYLE:OFF` comments

NOTE: `@SuppressWarnings` requires `SuppressWarningsFilter` under `Checker` and
`SuppressWarningsHolder` under `TreeWalker` in the Checkstyle configuration. Use the `aliasList`
property on `SuppressWarningsHolder` to map the MeaningfulMessage check to `MM-all` and avoid
`@SuppressWarnings("all")`, which disables all Checkstyle checks.

`MMShortTitle` in the diagnostic contract is a placeholder for the rule code format; use the
actual rule code (for example, `MMTooShort`) in suppressions.

MMMissingMessage can be suppressed, but should not be suppressed except as a last resort. Prefer
fixing the call site or annotation to supply a message or a throwable. For log calls, prefer an
inline `/* reason */` comment when a message must be omitted. Suppressing MMMissingMessage does not
skip the message-quality rules when a message is present.

== Supported Assertion Frameworks

The checker recognizes assertion methods from:

* *JUnit 4:* `org.junit.Assert.*`
* *JUnit 5:* `org.junit.jupiter.api.Assertions.*`
* *AssertJ:* `assertThat(...).as("message")`, `describedAs()`, `withFailMessage()`, `overridingErrorMessage()`
* *Hamcrest:* `org.hamcrest.MatcherAssert.assertThat("reason", actual, matcher)`
* *Java assert:* `assert condition : "message";`
* *TestNG:* `org.testng.Assert.*`

For JUnit assertions, message position follows the imported framework (JUnit 4 uses message first,
JUnit 5 uses message last). If both are present in the same file, the check avoids ambiguous
positions to reduce false positives.
For AssertJ message methods, only the first argument is treated as the message (format arguments
are ignored). For Hamcrest, the reason string is the first argument to `assertThat`.

Detection is based on method name patterns:

* Methods starting with `assert`
* Methods starting with `require`
* Method `fail`
* AssertJ chaining methods: `as`, `describedAs`, `withFailMessage`, `overridingErrorMessage`

Qualified calls are treated as assertions only when the qualifier resolves to a supported assertion
class (imported or fully qualified). Qualified calls to other types are ignored, even if JUnit
static wildcard imports are present. Prefer qualifying custom assertion helpers to avoid accidental
JUnit matching.

=== Excluded Methods

The following assertion-like methods are excluded because their string arguments are class/package names, not messages:

* `assertClassesLoad`
* `assertPackagePresent`
* `assertResourcePresent`

1. *Explain the invariant being tested*

[source,java]

+

[source,java]

== Detection Algorithm

=== Pseudocode

[source]
----
FOR each assertion method call in file:
    message = extractMessageParameter(call)

    IF message is missing or empty:
        CONTINUE  // Handled by separate PMD rule

    IF isExcludedContent(message):  // JSON, YAML, class names, etc.
        CONTINUE

    warningFired = false

    IF message seen before in this file:
        REPORT duplicate (with first occurrence line)
        warningFired = true
    ELSE:
        record message occurrence

    IF currentClassName exists:
        variant = findNameVariant(message, currentClassName)
        IF variant found:
            analysis = analyzeSubstance(message, variant)
            IF NOT analysis.hasSubstance:
                REPORT redundant_class with diagnosis
                warningFired = true

    IF currentMethodName exists:
        variant = findNameVariant(message, currentMethodName)
        IF variant found:
            analysis = analyzeSubstance(message, variant)
            IF NOT analysis.hasSubstance:
                REPORT redundant_method with diagnosis
                warningFired = true

    IF message matches line number pattern:
        REPORT redundant_line
        warningFired = true

    IF message matches generic single-word pattern:
        REPORT generic_message
        warningFired = true

    IF message matches assertion-type-repetition pattern:
        REPORT restates_assertion
        warningFired = true

    IF message matches index-only pattern:
        REPORT index_only
        warningFired = true

    IF message matches contextless-comparison pattern:
        REPORT contextless
        warningFired = true

    // Word metrics (skip word count if semantic warning already fired)
    FOR each word in message:
        IF word.length > MAX_WORD_LENGTH AND word != className AND word != methodName:
            REPORT long_word

    IF NOT warningFired:
        IF totalWordCount < minWordCount (per source):
            REPORT too_short
        ELSE IF totalWordCount > MAX_WORD_COUNT:
            REPORT too_long
        ELSE IF meaningfulWordCount < minMeaningfulWordCount (per source):
            REPORT too_few_meaningful
----

=== Substance Analysis Algorithm

[source]
----
FUNCTION analyzeSubstance(message, name):
    // Remove name from message (case insensitive)
    withoutName = message.replaceAll(name, " ")

    // Split into words and categorize
    filler = []
    meaningful = []

    FOR each word in withoutName:
        IF word in FILLER_WORDS OR isNumeric(word) OR word.length < 2:
            filler.add(word)
        ELSE:
            meaningful.add(word)

    hasSubstance = meaningful.size >= MIN_WORDS_WITHOUT_NAME

    // Generate diagnosis
    IF meaningful.isEmpty AND filler.isEmpty:
        diagnosis = "nothing remains after removing the name"
    ELSE IF meaningful.isEmpty:
        diagnosis = "only filler words remain: " + filler.join(", ")
    ELSE IF filler.isEmpty:
        diagnosis = "too short - only N word(s): " + meaningful.join(", ")
    ELSE:
        diagnosis = "only N meaningful word(s): " + meaningful.join(", ")
                  + " (filler: " + filler.join(", ") + ")"

    RETURN SubstanceAnalysis(hasSubstance, diagnosis)
----

== Examples

=== Violations

[source,java]
----
// VIOLATION: duplicate
assertEquals(a, b, "check value");  // line 10
assertEquals(c, d, "check value");  // line 20

// VIOLATION: lacks substance without class name
class BytesStoreTest {
    void test() {
        assertTrue(result, "BytesStore is valid");
        // → only 1 meaningful word: "valid" (filler: is)
    }
}

// VIOLATION: nothing remains without method name
void testWriteBuffer() {
    assertTrue(result, "testWriteBuffer");
}

// VIOLATION: generic single word
assertEquals(expected, actual, "value");

// VIOLATION: restates assertion
assertTrue(flag, "should be true");

// VIOLATION: line number
assertEquals(5, count, "L42");

// VIOLATION: index only
assertEquals(expected, array[0], "0");

// VIOLATION: contextless
assertEquals(a, b, "comparison");

// VIOLATION: too short
assertEquals(a, b, "check");

// VIOLATION: long word
assertEquals(a, b, "ConfigurationManagerServiceFactory failed");

// VIOLATION: trivial supplier
assertEquals(1, 1, () -> "constant");
----

=== Good Messages

[source,java]
----
// GOOD: explains invariant
assertEquals(5, activeUsers.size(),
    "active user count should be 5 after filtering inactive users");

// GOOD: business context
assertTrue(order.isValid(),
    "order should pass validation after setting customer and items");

// GOOD: specific data
assertEquals("AAPL", quote.getSymbol(),
    "market data feed should return AAPL as first symbol");

// GOOD: operation description
assertEquals(original, deserialized,
    "Chronicle Wire serialization should preserve all fields");

// GOOD: index with context
assertEquals(HEADER_MAGIC, buffer.getInt(0),
    "first 4 bytes should contain header magic number");

// GOOD: non-trivial supplier (lazy evaluation justified)
assertEquals(expected, actual,
    () -> "mismatch at index " + index + ": expected " + formatValue(expected));
----

== Testing Requirements

Each rule has:

1. Unit tests with `InputXxx.java` test fixtures demonstrating violations
2. Unit tests verifying no false positives on good messages
3. Integration tests against Chronicle codebase (smoke test)

Test fixtures cover:

* Multiple assertion frameworks (JUnit 4, JUnit 5, AssertJ)
* Edge cases (empty strings, unicode, special characters)
* Suppression mechanisms
* Exclusion scenarios (JSON, YAML, class names)
