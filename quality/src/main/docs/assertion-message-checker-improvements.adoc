= Assertion Message Checker Improvements Plan
:toc:
:toclevels: 3
:sectnums:

== Overview

This document outlines planned improvements to make assertion message warnings more **actionable, evidence-backed, and machine-parsable** for both humans and AI agents.

=== Goals

1. Standardize diagnostic format across all rules
2. Add stable rule codes for machine processing
3. Include matched evidence in all warnings
4. Provide small, safe fix hints
5. Support verbose mode for detailed diagnostics
6. Reference documentation anchors

=== Task 3: Extract Matched Tokens for Regex Rules

For regex-based rules, capture and report the actual matched substring.

==== Changes Required

1. **LINE_NUMBER_PATTERN**: Extract matched token (e.g., "L42", "line 42")
2. **INDEX_ONLY_PATTERN**: Extract matched index (e.g., "0", "[5]")
3. **CONTEXTLESS_PATTERN**: Extract matched phrase (e.g., "comparison")
4. **RESTATES_ASSERTION_PATTERN**: Extract matched phrase (e.g., "should be true")

.Implementation approach
[source,java]
----
// Instead of just checking if pattern matches, extract the match
private String extractMatch(Pattern pattern, String message) {
    Matcher matcher = pattern.matcher(message);
    if (matcher.find()) {
        return matcher.group();
    }
    return null;
}

// In checkMessage():
String lineMatch = extractMatch(LINE_NUMBER_PATTERN, message);
if (lineMatch != null) {
    log(lineNo, MSG_REDUNDANT_LINE, message, lineMatch);
    warningFired = true;
}
----

private static class SubstanceAnalysis {

    }
}

=== Task 9: Implement Additional Rules (Future)

==== AMQ13: Message Duplicates Assertion Input

Message duplicates a literal expected value, variable name, or exception class.

.Examples
[source,java]
----
// BAD - duplicates literal expected value
assertEquals("AAPL", symbol, "AAPL");

// BAD - duplicates variable name
assertTrue(flag, "flag");

// BAD - duplicates exception class
assertThrows(IOException.class, () -> ..., "IOException");
----

.Detection approach
* For common signatures, check if message literal equals:
** A literal expected value
** The simple identifier name of expected/actual
** The simple exception class name in assertThrows

==== AMQ14: assertAll Heading Quality

JUnit `assertAll(String heading, ...)` includes the heading in failure reports.

.Examples
[source,java]
----
// BAD - low signal heading
assertAll("assertAll",
    () -> assertEquals(a, b),
    () -> assertEquals(c, d));

// GOOD - describes scenario/phase
assertAll("round-trip serialisation: header + trailer",
    () -> assertEquals(a, b),
    () -> assertEquals(c, d));
----

.Detection approach
* Run headings through existing semantic rules (generic/restates/contextless/too-short)
* If assertAll has N>=3 executables and heading is absent, emit suggestion (not error)

==== AMQ15: Restates Derived Assertion

Expand "restates assertion" to common derived patterns that frameworks already show.

.Patterns to detect
----
^(is )?empty$
^not empty$
^(is )?blank$
^not blank$
^(is )?present$
^contains$
^matches$
----

.Examples
[source,java]
----
// BAD - framework already shows "empty"
assertThat(list).as("empty").isEmpty();

// GOOD - says what should be empty and why
assertThat(list).as("filtered results after applying blacklist").isEmpty();
----

==== AMQ16: AssertJ Generic Override (P2)

AssertJ docs note that `as(...)` descriptions preserve rich diff output, while `withFailMessage()`/`overridingErrorMessage()` can hide context.

.Detection approach
* If `.withFailMessage(...)` or `.overridingErrorMessage(...)` message is generic/too-short/restates, suggest `.as(...)` instead

.Reference
* https://assertj.github.io/doc/[AssertJ documentation]

==== AMQ17: Cheap Supplier (P2 - Optional)

Complement to trivial supplier: if supplier body is "cheap" (short literal or trivial concat), prefer plain string.

.Rationale
* JUnit message suppliers are evaluated lazily only on failure
* Supplier is mainly for expensive construction
* Lambda overhead may matter in cold-start scenarios

.Detection approach
* Lambda body contains only: string literals, simple concatenation, or constant field access

== Diagnostic Contract

=== Message Structure

Every warning follows this structure:

----
[AMQnn] <Problem statement>. Why: <Evidence>. Fix: <Action>. Ref: <anchor>
----

.Components
[cols="1,3"]
|===
|Component |Description

|`[AMQnn]`
|Stable 5-character rule code (AMQ + 2 digits)

|Problem statement
|What is wrong (present tense, concise)

|Why
|Evidence that triggered the rule (matched token, counts, breakdown)

|Fix
|Concrete action to resolve (imperative, safe suggestion)

|Ref
|Documentation anchor for detailed guidance
|===

=== Verbosity Levels

[cols="1,2,2"]
|===
|Mode |Output |Use Case

|`verbose=false` (default)
|Single line with code, problem, why, fix, ref
|CI logs, Maven output

|`verbose=true`
|Above + `Details:` suffix with full breakdown
|Local development, debugging
|===

=== Sample Outputs

==== CI Mode (default)
----
[WARNING] MyTest.java:[42] (extension) UniqueAssertMessages: [AMQ02] Message "BytesStore should be init" depends on method name "bytesStore". Why: only 1 meaningful word(s): init (filler: should, be). Fix: add 2+ meaningful words that survive without the name. Ref: assertion-messages.adoc#AMQ02
----

==== Verbose Mode
----
[WARNING] MyTest.java:[42] (extension) UniqueAssertMessages: [AMQ02] Message "BytesStore should be init" depends on method name "bytesStore". Why: only 1 meaningful word(s): init (filler: should, be). Fix: add 2+ meaningful words that survive without the name. Ref: assertion-messages.adoc#AMQ02 Details: meaningful=[init] filler=[should,be] removed=[bytesStore] original=[BytesStore should be init]
----

== Migration Notes

=== Backward Compatibility

* New message format is breaking change for any tooling parsing exact message text
* Rule codes are additive and stable once assigned
* Verbose property defaults to false (no change in default output length)

=== Suppression Updates

Existing suppressions continue to work (based on check name, not message text).

=== AI Agent Integration

AI agents can:

1. Parse rule code to select appropriate rewrite strategy
2. Use "Why" section to understand trigger condition
3. Use "Fix" section as transformation hint
4. Follow "Ref" anchor for detailed house style rules
5. Enable verbose mode when debugging transformations
