= Metadata and Diagnostic Message Quality Research Topics
:toc:
:toclevels: 3
:sectnums:

Below are research topics that map directly to automated checks you can run in CI (and also use for "linting" new or changed messages). It includes concrete search keywords and anchor specs or guides worth reading.

== Metadata description quality

=== 1) JUnit display metadata consistency rules

What to research::
* Patterns for `@DisplayName`, parameterised invocation names, and centrally configured default name patterns.
* How parameter names are surfaced in parameterised display names (build flags, language specifics).

Why it helps triage::
* Better test report readability and faster "what failed?" scanning.

Anchors::
* link:https://docs.junit.org/5.10.2/user-guide/?utm_source=chatgpt.com[JUnit 5 User Guide]

Keywords::
* `JUnit 5 DisplayName guidelines`
* `junit.jupiter.displayname.generator`
* `ParameterizedTest name pattern junit.jupiter.params.displayname.default`

=== 2) "Disabled reason" quality gates

What to research::
* Enforce: who disabled, why, when to re-enable, link to ticket or runbook.
* Anti-pattern detection: "temporarily", "flaky", "fix later".

Keywords::
* `@Disabled reason best practice`
* `test quarantine policy`
* `flaky test triage metadata`

=== 3) Ownership and runbook metadata schema

What to research::
* Minimum fields for ownership (`team`, `service/component`, `oncall`, `runbook_url`, `severity/impact`).
* Whether to embed as annotations or tags in tests vs a central registry (or both).

Keywords::
* `service ownership metadata taxonomy`
* `runbook link conventions`
* `component taxonomy SRE`

=== 4) Environment and build provenance metadata (and how to standardise it)

What to research::
* Standard fields for `service.name`, `deployment.environment.name`, version and build identifiers.
* Where to attach them (resource attributes vs log attributes).

Anchors::
* link:https://opentelemetry.io/docs/specs/semconv/resource/?utm_source=chatgpt.com[OpenTelemetry resource semantic conventions]

Keywords::
* `OpenTelemetry resource attributes build version`
* `deployment.environment.name`
* `service.name uniqueness`

=== 5) Metadata validation via schemas and policy-as-code

What to research::
* Express required or optional fields, controlled vocabularies, and uniqueness constraints using JSON Schema.
* Enforce additional rules (for example, "runbook must be present when severity >= S2") using OPA/Rego (Conftest-style workflows).

Anchors::
* link:https://json-schema.org/draft/2020-12/json-schema-validation?utm_source=chatgpt.com[JSON Schema validation vocabulary]
* link:https://openpolicyagent.org/docs/configuration?utm_source=chatgpt.com[OPA configuration]

Keywords::
* `JSON Schema required properties`
* `schema linting CI`
* `OPA Rego conftest linting YAML`

== Diagnostic message quality

=== 6) Actionable message design (human factors)

What to research::
* Message structure: plain language, precise cause, concrete next step, avoid blame.
* Localisation and consistency considerations (tense, voice, terms).

Anchors::
* link:https://learn.microsoft.com/en-us/windows/win32/debug/error-message-guidelines?utm_source=chatgpt.com[Microsoft error message guidelines]

Keywords::

* `plain language error text`

=== 7) Structured logging fields and semantic conventions (machine triage)

* Which fields should always exist: `trace_id`, `span_id`, `service.name`, `deployment.environment`, `exception.*`, plus domain keys.
* Adopt OpenTelemetry log semantic conventions for consistency across services.

Anchors::

=== 11) Template discipline and high-cardinality controls

What to research::
* Rules for message templates: keep stable text and put variable data in fields or structured attributes.

Keywords::
* `log message cardinality`
* `message template hashing`
* `structured logging anti patterns`

* `diagnostic linting`

== Cross-cutting checker design topics

=== 14) Where to enforce: compile-time, test-time, or ingest-time

What to research::
* Trade-offs between:
** compile-time (annotation processors, static analysis),
** test-time (JUnit extensions or listeners),
** ingest-time (log pipeline rules, schema enforcement).

Keywords::
* `policy enforcement layers observability`
* `CI lint vs runtime validation`

=== 15) Governance: controlled vocab and drift management

What to research::
* How to manage allowed component, team, and severity values, deprecate terms, and handle migrations without breaking searches or dashboards.

Keywords::
* `controlled vocabulary governance`
* `schema evolution`
* `data contracts observability`

=== 18) Correlation and baggage propagation from test runner to SUT

What to research::

* Allowlist and redaction rules for baggage keys to avoid leaking identifiers.

Keywords::
* `W3C traceparent propagation`
* `OpenTelemetry baggage allowlist`
* `test harness correlation id`

=== 19) Diagnostic quality scorecard and diff-scoped gating

What to research::
* A measurable score for actionability, traceability, and structure, with thresholds for new or changed messages.
* Trend monitoring to catch gradual drift rather than only per-change regressions.

Keywords::
* `message quality metrics`
* `diff scoped linting`
* `quality gate new code`

=== 20) Privacy and security scanning for diagnostics

What to research::
* PII and secret scanning applied to logs, test reports, and attachments, not just source files.
* Redaction markers and safe external vs internal diagnostic channels.

Keywords::
* `log PII redaction`
* `secret scanning logs`
* `CWE-209 error message exposure`

=== 21) Performance and cost controls for diagnostics

What to research::
* Zero-allocation or low-allocation logging patterns and guidance for hot paths.
* Payload size caps, sampling policies, and rate limiting for diagnostic events.

Keywords::
* `zero allocation logging Java`
* `log cardinality control`
* `OpenTelemetry tail sampling`

== Prioritisation by impact and ease (Maven-first)

The ordering below favours checks that can run as part of the Maven build (Checkstyle, PMD, SpotBugs, Error Prone, ArchUnit, Surefire).

=== P0: High impact, easy to automate in Maven

Automatable now::
* Exception message quality: Error Prone check for variable-only messages and ArchUnit ban on generic exceptions.
* Assertion and log message linting: extend Checkstyle rules and align with PMD or SpotBugs message checks.
* JUnit metadata consistency: Surefire phrased names and a fixture test that asserts display names and disabled reasons are preserved.

Gen AI later::
* Draft contextual messages for exceptions and assertions.
* Suggest DisplayName and Disabled reason improvements based on test context.

Human judgement::
* Approve naming conventions for DisplayName and Disabled reasons.
* Decide where messages are mandatory (exceptions, logs, assertions).

=== P0 coverage and gaps (MeaningfulMessage)

Current coverage::
* Assertions, preconditions, throw messages, and annotation descriptions are checked for low-signal patterns (generic, too short, too few meaningful, line numbers, whitespace runs).
* Duplicates are checked for assertions and annotations; class or method redundancy and missing subject apply only to assertions.

Automatable gaps::
* Exception messages: require non-empty messages for common exception types (IllegalArgumentException, IllegalStateException, UnsupportedOperationException, AssertionError); flag variable-only messages or ones that just restate the exception type. For low-latency or high-performance classes, allow an explicit suppression on the class or method to waive the message requirement, but require messages by default elsewhere.
* Log sites: apply core MeaningfulMessage checks to SLF4J `trace/debug/info/warn/error`, Log4j2 `trace/debug/info/warn/error/fatal`, JUL `java.util.logging.Logger`, `System.Logger`, and Chronicle `Jvm.*.on(...)` calls (generic, too short, too few meaningful, contextless, index-only, missing subject, whitespace runs). Treat duplicate messages as a lower-severity signal. For `Jvm.*.on(...)` callsites, require a non-null message or a throwable (null templates without a throwable are missing-message failures), enforced by `MMMissingMessage`. Empty templates are treated as present and fail via MMTooShort/MMTooFewMeaningfulWords, even when a throwable is supplied. For SLF4J, Log4j2, JUL, and System.Logger, empty templates are handled by MMTooShort/MMTooFewMeaningfulWords rather than a missing-message rule. Null templates are missing-message failures unless any argument is a known throwable, regardless of additional arguments. "Known throwable" means any subtype of `Throwable` (including `StackTrace`), type-based only (no name-based guessing). If a throwable is present, the message is optional but must be meaningful when provided. For SLF4J, Log4j2, JUL, and System.Logger, treat varargs as placeholders and do not infer throwable position.
* Missing metadata: `MMMissingMessage` also covers `@Disabled`/`@Ignore` with no reason.
* Missing-message rules for `Jvm.*.on(...)` treat only null messages without a throwable as missing;
  empty templates are present and fail via MMTooShort/MMTooFewMeaningfulWords.
* DisplayName annotations: apply the core MeaningfulMessage checks (generic, too short, too few meaningful, line numbers, whitespace runs, duplicates), while allowing JUnit standard placeholders (`{index}`, `{arguments}`, `{argumentsWithNames}`, `{displayName}`, `{0}`).
* Message-required cases: consider PMD UnitTestAssertionsShouldIncludeMessage (tests) and require messages for Objects.requireNonNull or similar preconditions in production code.

=== P1: High impact, medium effort (Maven plus auxiliary tooling)

Automatable now::
* YAML spec schema validation and TitleCase rule registry checks (run via Maven exec or a small Java tool).
* Spec-to-rewrite binding tests and idempotency checks for OpenRewrite or Refaster recipes.
* Privacy and secret scans of test reports and attachments as an optional Maven profile.

Gen AI later::
* Emit YAML specs that fill in structured fields and remediation hints.
* Propose rule registry entries with risk tier metadata.

Human judgement::
* Approve risk tiers and deprecation policy for rules.
* Review medium-confidence changes and adjust schema constraints.

=== P2: High impact, harder to automate (cross-system or integration heavy)

Automatable now::
* Correlation and baggage propagation integration tests across the test runner and SUT.
* Structured logging field presence checks for OpenTelemetry and ECS mappings in config.

Gen AI later::
* Generate campaign reports with sampling suggestions and summaries.
* Propose migration notes for schema or logging changes.

Human judgement::
* Accept or reject semantic diff invariants and provenance requirements.
* Tune sampling, retention, and privacy policies for production use.

=== Deferred: standardised error codes

Future improvement::
* Define a stable error code taxonomy and enforce it for exception messages once the message-quality checks are in place.
